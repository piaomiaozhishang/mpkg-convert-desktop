# 两套方法对比与融合建议

> 对象 A = 本项目的交接包（`D:\pro-workbuddy\壁纸转原图\handoff\`，我做的）
> 对象 B = 经验包 `wallpaper-mpkg提取经验包.zip`（另一 agent 做的）
> 结论基于对**同一个** `.tex` 文件的双路实跑对照（见下文「实证」一节）。

---

## 0. 一句话结论

**两套方法都对，而且是逐像素等价的** —— 它们解出的原图 RGB 像素 sha256 完全相同
（`b5d2736c340645bc237c372dfa59b68619fc9c0e0b59bbe1b40fc1cbfbc75dea`），
也都等于经验包 B 里那张「人工核对基准 PNG」。

但两者**代码路线和验证方法学完全不同**：
A 走**自写零依赖 CPU 解码器 + 像素级/测试向量验证**；
B 走**现成库（texture2ddecoder）+ 缩略图统计比对**，Android 侧给的是 **GLES3.0 硬件解码**。
→ **建议以 A 为基座，把 B 的 GLES 加速路径与格式兼容表融合进去**（已产出 v2 包）。

---

## 1. 两者各自是什么

| | A（我的包） | B（经验包） |
|---|---|---|
| 核心理念 | 自己实现解码器，做到「可证明正确」 | 站在现成库肩膀上，快速跑通 + 给 Android 一条 GPU 捷径 |
| `.mpkg`/`.tex` 解析 | 自写（Python 零依赖 + Kotlin） | 自写（Python 零依赖 + Kotlin 片段） |
| LZ4 | 纯 Python + Kotlin，自写 | 纯 Python + **纯 Java**（`Lz4Block.java`），自写 |
| ETC2_RGBA8 解码 | **自写** `pure_etc2.py`（零依赖）/ `Etc2Rgba8Decoder.kt` | 调 `texture2ddecoder.decode_etc2a8`（第三方 C 扩展） |
| Android 解码路径 | **纯 CPU Kotlin**（后台线程、无 GL 上下文） | **GLES3.0 硬件**（`glCompressedTexImage2D` + FBO + `glReadPixels`） |
| 验证手段 | 测试向量 + 与 oracle 逐块比对 + 像素 sha256 + 与 preview 逐通道 NCC | 与 preview 的**平均色 / MAD**（低分辨率缩略图）比对 |
| 依赖 | 零（核心） | `pillow` + `texture2ddecoder` |

**共同点（两边独立得到、互相印证）**：
`Format=5 = ETC2_RGBA8`；16B 块 = [8B EAC alpha][8B ETC2 RGB]；
不透明指纹前 8 字节恒为 `FF 00 00 00 00 00 00 00`（实测 518400/518400 块命中）；
mip 是**裸 LZ4 block**；`TEXB0004` 非 MP4 走 `TEXB0003` 版式；
`.mpkg` 目录项 offset 相对「目录表结束位置」。

## 2. 实证：把两套方法放同一个文件上跑

同一个 `.tex`（sha256 `991365999029b390e6b955f4e1695984e9aa4b578d213e07a3e5dd70489ef729`，
A 包的 `sample/texture.tex` 与 B 包解出来的 `.tex` 是同一个文件）：

| 解码路径 | 与参考原图的**不同像素数** | RGB 像素 sha256 |
|---|---|---|
| A：`pure_etc2.py`（**不交换** R/B） | **0 / 8294400** | `b5d2736c…cbfbc75dea` ✅ |
| B：`texture2ddecoder` 原始输出（不交换） | 7919837 / 8294400 | `a095a7c6…` ❌ |
| B：`texture2ddecoder` **交换 R/B** 后 | **0 / 8294400** | `b5d2736c…cbfbc75dea` ✅ |

→ **A 与 B 最终产物逐像素完全相同。**

### 关键纠正：关于「BGR」的真相

两边一度都得出「ETC2 解出来是 BGRA，要交换 R/B」。**这个说法只有一半对**：

- **ETC2_RGBA8 这个格式本身解出来就是 RGBA**，**不应该**交换。
- 之所以看起来像 BGR，是**因为 `texture2ddecoder.decode_etc2a8` 这个库返回的是 BGRA**。
  用这个库才需要交换；用自写解码器不需要。

所以 B 包的写法（库 + 交换）**结果正确**，但它写在文档里的心智模型
「ETC2 解码结果通道顺序是 BGRA」是**错的**——如果接手方后来换成自写/GLES 解码，
照着这句话去交换 R/B，就会把图弄反。**这是我建议在融合版里明确纠正的一点。**

## 3. 逐项对比：谁更好

| 维度 | 胜出 | 说明 |
|---|---|---|
| **正确性可证明性** | **A** | A 有像素 sha256 硬基准 + 60 组 ETC2 测试向量 + LZ4 fuzz + 与 oracle 逐块比对；B 包内只有「与基准 PNG 逐像素相同」的**口头断言**，没有可复现的验证产物 |
| **零依赖 / 可移植** | **A** | A 核心零依赖；B 依赖 `texture2ddecoder`（且正是它引入了通道序坑） |
| **Android 解码性能** | **B** | GLES3.0 硬件解码，天然快；A 的 CPU 版在 JVM 实测 4K 105 ms（够用，但低端机不如 GPU） |
| **Android 工程确定性** | **A** | A 的 CPU 解码器有测试向量、结果确定、可在后台线程跑；GLES 需要 EGL 上下文 + FBO，且 B 自己也标注「通道序要在设备上验证」 |
| **桌面快速侦察 / 格式发现** | **B** | B 用 `texture2ddecoder` 一次性暴力扫了 bc1/3/4/5/6/7、astc、etc1、etc2a1、etc2a8，思路很实用 |
| **多格式覆盖（Python 参考）** | **B** | B 的 `tex_decode.py` 覆盖 Format 0/4/5/6/7/12 分派；A 的纯解码器只做了 0 和 5 |
| **格式文档完备度** | **平** | B 的 `.tex` 实测偏移表（0x12→0x5B）非常清楚；A 的规格文档更细到比特位（ETC2 各模式的位域） |

### 双方各自的短板

- **A 的短板**：Android 只给了 CPU 路径，没有 GPU 加速选项；Python 参考只覆盖 ETC2/RGBA8888。
- **B 的短板**：
  1. 文档里「ETC2 解出来是 BGRA」的**心智模型是错的**（见 §2）；
  2. 验证方法学有瑕疵——它把**整张 3840×2160 全图**缩到 480×270，去和 **preview.jpg（1024×1024 方形裁剪）**比，
     两者根本没对齐，MAD 被错位噪声污染（所以它报的 MAD 53.6/43.0 都很大，只能做「相对排序」）。
     正确做法是**先裁剪再降采样**（A 的 `verify.py` 就是这么做的：裁 x[1254,3414] → 1024² → 逐通道 NCC 0.998）；
  3. **没有测试向量**，接手方无法自证；
  4. 光看它包内的证据，无法排除「它其实也踩过通道序坑、只是恰好选对了」。

> 顺带一个踩坑提醒：**灰度 NCC 几乎无法判别 R/B 是否交换**。
> 实测灰度 luma NCC：不交换 0.9988、交换后仍有 0.9655（差异很小）；
> 换成**逐通道** NCC 才拉到 0.9977 vs 0.5685。做通道序验证必须用逐通道或像素级。

## 4. 谁更好？——分场景

- **要「可证明正确 + 可复现 + 零依赖」的参考实现** → **A 更好**（这也是交接给 Android agent 的关键）。
- **要「几分钟跑通、以便快速确认格式」** → **B 更省事**。
- **要「Android 上最快」** → **B 的 GLES 路径更好**，但需要设备实测。
- **作为交给「做安卓转换软件」的 agent 的交接产物** → **A 是更好的基座，B 提供最好的补充。**

→ 结论：**融合**，而不是二选一。

## 5. 融合清单（已落地到 v2 包）

把 B 的优点并入 A 的基座：

| 从 B 融合进来 | 用途 |
|---|---|
| `android/Etc2Gles.kt`（GLES3.0 硬件解码） | 给 Android 一条**可选 GPU 加速路径**（低端机 / 大批量时更快） |
| `COMPAT_FORMATS.md`（Format 枚举 + Android 可行性表） | 遇到其它格式（0/4/6/7/12）时知道能不能做、怎么做 |
| `.tex` 实测偏移表 | 并入规格文档，便于快速定位 |
| 「暴力扫格式」的思路 | 作为发现未知 Format 的方法学写进文档 |

同时把 A 的验证 rigor 补进 B 的盲点：

| 补进融合版 | 用途 |
|---|---|
| 像素 sha256 硬基准 + 测试向量 | 任何解码实现都能自证 |
| 逐通道 NCC 验证脚本 | 正确判别通道序 |
| 零依赖解码器 | 不引入库、不引入通道序坑 |
| 「ETC2 本体是 RGBA，勿交换；BGRA 是某库的假象」的正名 | 防止接手方照抄错的心智模型 |

## 6. 融合后 Android 端建议的代码骨架

```
默认路径（推荐，确定性强、已带测试向量）：
  MpkgParser → TexParser → Lz4BlockDecoder → Etc2Rgba8Decoder(CPU) → Bitmap
可选加速路径（低端机/批量，需在目标机验证）：
  MpkgParser → TexParser → Lz4BlockDecoder → Etc2Gles(ETC2 压缩纹理→FBO→glReadPixels) → Bitmap
两者输出必须与 testdata 里的像素 sha256 基准一致
```

CPU 与 GPU 两条路径互为对照：**用 CPU 路径的输出去校验 GPU 路径**，可以一次性排掉
GLES 的垂直翻转与通道序两个经典坑。
